## Summary

This release keeps all fork-specific persistent pin behavior from `v2026.04.20-persistent-pin.5` and adds a new optional built-in `tsnet` subsystem.

The new subsystem lets `mihomo` run as its own tailnet node without managing system `tailscaled`, without using TUN/TAP, and without acting as a system VPN.

The first release scope is intentionally small:

- maintain a persistent embedded tailnet identity
- expose the existing ordinary controller on the tailnet when enabled
- expose a standard SOCKS5 service on the tailnet when enabled
- allow standard `socks5` proxy entries to reach peer `mihomo` nodes through tailnet IP or MagicDNS names

## What Is New

### Built-in `tsnet` node

- Adds an embedded `tsnet.Server`.
- Uses `state-dir` as the persistent node identity root.
- Generates stable node names like `mihomo-<short-id>`.
- Does not depend on host `tailscaled`.
- Does not bind host TUN/TAP.
- Does not create a system VPN interface.
- Does not modify host Tailscale state.

### Native Headscale/Tailscale authorization flow

- No YAML `preauthkey`.
- The embedded client starts the native login/authorization flow.
- Logs pending authorization state and auth URL when `tsnet` provides one.
- After approval, the node reaches `connected`.
- If the server requires machine authorization again, state becomes `needs-reauth`.

### Tailnet SOCKS5 mesh

- Optional tailnet-only SOCKS5 listener.
- Configured by `tailscale.mesh` and `tailscale.socks5`.
- Listens on the tailnet, not host loopback or LAN.
- Supports TCP CONNECT and UDP ASSOCIATE.
- Reuses existing mihomo tunnel handling and proxy chains.
- Reuses existing SOCKS auth store.
- Does not apply host `allow-lan` filtering to tailnet peers.

### Standard SOCKS5 outbound reuse

- No new proxy type.
- No magic proxy name.
- No special server field.
- Existing `socks5` nodes are used.
- If `tsnet` is ready and the SOCKS5 node port equals `tailscale.socks5`, mihomo first tries `tsnet` dial.
- If that fails, it falls back to the original dialer.
- This preserves compatibility with normal SOCKS5 behavior.

### Controller over tailnet

- Optional exposure of existing ordinary `external-controller`.
- Reuses existing controller route handler.
- Reuses secret, CORS, debug, and DOH controller settings.
- Does not expose `external-controller-tls`, unix socket, or pipe controller in this first version.
- Does not create another host listener.

### Minimal tailnet SOCKS hardening

- Tailnet SOCKS handshake timeout: `10s`.
- Tailnet SOCKS active TCP/control connection cap: `1024`.
- Active cap covers TCP CONNECT and UDP ASSOCIATE control connections.
- Cap warning is rate-limited to `30s`.
- UDP data still uses existing mihomo queue/NAT/timeout behavior.

## Configuration

Minimal enabled config:

```yaml
tailscale:
  enable: true
  login-server: https://hs.example.com
  state-dir: tailscale
  expose-controller: true
  mesh: true
  socks5: 1666
```

Default config:

```yaml
tailscale:
  enable: false
  login-server: ""
  state-dir: tailscale
  expose-controller: false
  mesh: false
  socks5: 1666
```

Use a peer node by tailnet IP:

```yaml
proxies:
  - name: tail-socks-home
    type: socks5
    server: 10.20.0.33
    port: 1666
    udp: true
```

Use a peer node by MagicDNS or Headscale DNS name:

```yaml
proxies:
  - name: tail-socks-name
    type: socks5
    server: peer-node33.example.internal
    port: 1666
    udp: true
```

Use that SOCKS5 node as a standard `dialer-proxy`:

```yaml
proxies:
  - name: tail-socks-home
    type: socks5
    server: 10.20.0.33
    port: 1666
    udp: true

  - name: ss-through-home-tail
    type: ss
    server: example.com
    port: 443
    cipher: chacha20-ietf-poly1305
    password: "password"
    udp: true
    dialer-proxy: tail-socks-home
```

## Runtime Flow

### First start

1. `mihomo` parses the `tailscale` block.
2. If enabled, it validates `login-server`, `state-dir`, and `socks5`.
3. It locks `state-dir`.
4. It generates or reuses `mihomo-instance-id`.
5. It starts `tsnet.Server`.
6. It waits for control-plane state.
7. If authorization is pending, it logs `unregistered`.
8. If `tsnet` exposes an auth URL, it logs that URL.
9. User approves the node from Headscale/Tailscale.
10. Runtime moves to `connected`.

### Normal restart

1. Same `state-dir` is reused.
2. Same local identity is reused.
3. Same node name is reused.
4. Tailnet IP should remain stable as long as control-plane policy keeps that node/IP.
5. Mesh SOCKS and controller expose restart after connection.

### Config reload

1. Old runtime is stopped.
2. Old listeners are closed.
3. Old UDP packet conns are closed.
4. Old controller listener is closed.
5. Old `state-dir` lock is released.
6. New config starts a fresh runtime.

## Error Handling

Config-load failures:

- `tailscale.enable=true` with empty `login-server`
- `tailscale.enable=true` with empty `state-dir` after defaults
- `tailscale.socks5 < 1`
- `tailscale.socks5 > 65535`
- unsafe `state-dir`

Runtime-only failures:

- `state-dir` lock failure disables only the `tsnet` subsystem
- pending authorization sets `unregistered`
- machine authorization requirement sets `needs-reauth`
- backend or watch errors set `register-failed`
- mesh SOCKS TCP listener failure disables mesh until on-use retry
- mesh UDP listener failure disables UDP relay until on-use retry
- controller expose failure disables only tailnet controller exposure

Retry behavior:

- Mesh listener retry is usage-triggered.
- Retry starts at `10s` and backs off exponentially.
- No background retry timer is used for mesh listener recovery.

## Compatibility Notes

- Existing persistent-pin configuration and behavior remain available.
- `tailscale.enable=false` keeps the new subsystem fully off.
- The new `tailscale` block is optional.
- `mesh=false` means no tailnet SOCKS5 listener is created.
- `expose-controller=false` means controller is not exposed through tailnet.
- No proxy group, rule, provider, health check, or global DNS behavior is intentionally changed.
- SOCKS5 nodes that do not use `tailscale.socks5` port keep their previous behavior.

## Known Limits

- Real Headscale/Tailscale authorization must still be validated by CI/user environment after deployment.
- The feature does not provide automatic approval.
- The feature does not promise stable IP without persistent `state-dir`.
- The feature does not expose TLS/unix/pipe controller variants.
- The feature does not implement SOCKS5 mux.
- UDP flow limits are inherited from existing mihomo tunnel/NAT behavior.
