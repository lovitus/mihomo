## What Changed Relative to `.4`

This release does not change the fork runtime behavior contract.

It fixes the release workflow so the fork build pipeline matches upstream patch usage again.

Specifically:

- `.4` carried back an old fork `build.yml` patch dependency set
- the repository content on this branch only included upstream `.github/patch/issue77930.patch`
- the workflow still tried to apply missing files such as:
  - `issue77731.patch`
  - `issue77975.patch`
  - `go1.26.patch`
  - `go1.25.patch`
  - `go1.24.patch`
  - `go1.23.patch`
  - `go1.22.patch`
  - `go1.21.patch`
- this caused the build matrix to fail immediately

`v2026.04.20-persistent-pin.5` fixes that mismatch by aligning the fork workflow with upstream `v1.19.24` patch usage.

## Root Cause of `.4` Failure

The failing workflow step in `.4` was:

- `Apply issue77731 for Golang1.26`

The failing build job was first observed in:

- `build (linux, mips64, mips64)`

The failure reason was:

```text
.github/patch/issue77731.patch: No such file or directory
```

This was not a runtime code bug.
It was a workflow dependency mismatch.

## Workflow Correction in `.5`

The release workflow is now aligned with upstream `v1.19.24`:

- keeps upstream patch dependency model
- keeps only upstream-available local patch usage
- removes old fork-only patch references that are not present in this branch

Fork-specific workflow behavior still retained:

- `Upload-Tag-Release` remains enabled for `v*` tag pushes
- Docker publish path remains disabled in this fork

## Runtime Behavior Status

The runtime behavior preserved by `.4` is still the runtime behavior of `.5`:

- `fallback` keeps first-alive ordered selection semantics
- `fallback` does not prefer timeout nodes when alive alternatives exist
- `url-test` does not choose timeout nodes when alive alternatives exist
- `persistent-pin` behavior is preserved
- auto-unfix threshold logic is preserved
- reset-on-recovery / reset-on-successful-record / reset-on-no-alternative logic is preserved
- `/groups/{name}/delay` still preserves persistent pin when enabled
- JSON output still exposes persistent pin fields
- parser semantics for unset / `0` / invalid values are preserved
