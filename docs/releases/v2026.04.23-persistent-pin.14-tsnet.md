## Summary

This release does not change runtime behavior.

It documents an intentional tsnet SOCKS5 UDP design choice: when a tailnet SOCKS5 UDP ASSOCIATE response returns an unspecified UDP bind address, mihomo keeps the existing small implementation and does not add tailnet identity lookup, peer cache lookup, or MagicDNS relay-address resolution.

If that best-effort tsnet UDP path cannot resolve or bind, the existing implementation closes the tsnet control connection and retries once through the original default dialer path. If the default path also fails, the caller receives the normal SOCKS5 UDP error.

## What Changed

- Added an inline code comment in `adapter/outbound/socks5.go` explaining why unspecified UDP bind address handling does not grow tailnet identity or MagicDNS resolution logic.
- Added this release note with branch, parent, previous-release, validation, behavior, and abnormal-path handling details.
- Updated `docs/tailscale-tsnet.md` so future maintainers do not treat this best-effort fallback behavior as an accidental omission.

## What Was Fixed

This is a documentation and maintenance-safety release.

It fixes the review and maintenance ambiguity around this scenario:

- tsnet is ready
- a SOCKS5 outbound matches `tailscale.socks5`
- UDP ASSOCIATE succeeds far enough to return an unspecified BND.ADDR such as `0.0.0.0:<port>`
- resolving the SOCKS5 server name through the ordinary resolver may miss a private tailnet-only name

The intended behavior is not to add a larger identity-resolution subsystem for this edge case. A miss is safe because tailnet addresses are private and the implementation already falls back to the original dialer path.

## Behavior Changes

No runtime behavior changes.

The code path remains:

1. Try tsnet first only when tsnet is ready and the SOCKS5 server port equals `tailscale.socks5`.
2. For SOCKS5 UDP ASSOCIATE, use the same selected TCP control path.
3. If the tsnet TCP, SOCKS5 UDP handshake, UDP bind address handling, or tsnet PacketConn path fails, retry once through the original default dialer path.
4. If the default path also fails, return the error.

The release intentionally does not add:

- peer identity cache
- tailnet peer IP lookup
- MagicDNS-specific relay-address resolution
- self-loop blocking
- stricter no-fallback UDP semantics
- new YAML options

## Abnormal Path Handling

Expected abnormal paths and their handling:

- `tsnet` is not connected: use the original dialer path directly.
- tsnet TCP dial fails: log debug information and fall back to the original dialer path.
- tsnet UDP ASSOCIATE fails: close the tsnet control connection and fall back to the original dialer path.
- UDP BND.ADDR is invalid: close the tsnet control connection and fall back to the original dialer path.
- UDP BND.ADDR is unspecified and ordinary resolver misses: close the tsnet control connection and fall back to the original dialer path.
- tsnet PacketConn creation fails: close the tsnet control connection and fall back to the original dialer path.
- original dialer fallback also fails: return the original error to the caller.

These paths are considered acceptable for the minimal tsnet integration because they either recover through the default path or fail closed for a private tailnet address.

## How To Use

Existing tsnet configuration remains unchanged:

```yaml
tailscale:
  enable: true
  login-server: https://hs.example.com
  state-dir: tailscale
  expose-controller: true
  mesh: true
  socks5: 1666
```

Recommended SOCKS5 peer configuration remains tailnet IP first:

```yaml
proxies:
  - name: tail-socks-home
    type: socks5
    server: 10.20.0.33
    port: 1666
    udp: true
```

MagicDNS or Headscale DNS names remain best-effort:

```yaml
proxies:
  - name: tail-socks-name
    type: socks5
    server: peer-node33.example.internal
    port: 1666
    udp: true
```

If UDP through a tailnet DNS name is temporarily unavailable, use the peer tailnet IP or rely on the existing fallback behavior. No YAML migration is required for this release.
